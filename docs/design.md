# Design

agent-worktrees owns the lifecycle of a task checkout: a git worktree at a conventional path, set up by the project's own script, when it has one, before an agent works in it, and torn down by the project's own script, when it has one, before it goes. Claude Code reaches it through the `cniska-worktrees` plugin, which tells each session to use the commands and sends Claude Code's own worktree creation and removal through them, and a person or another tool reaches it through the same commands.

## Why a tool, not git hooks

On every worktree it creates itself, Claude Code points the shared `core.hooksPath` at the primary's `.git/hooks` (that directory always exists, so the write always happens), which overrides a project's `.githooks` wiring for every checkout at once. A `post-checkout` hook would therefore run for a while and then stop. With a `WorktreeCreate` hook configured, Claude Code skips its own creation and post-creation setup entirely and takes the path the hook prints, so the project's setup runs under the tool's control and git's hook configuration is left alone.

## Claude Code plugin

The plugin carries two kinds of hook. Its SessionStart hook adds `plugin/hooks/note.md` to the session's context on startup, resume, clear and compact; the note goes to every session, whatever directory it starts in, since a session works in more repositories than the one it starts in and every repository works with the tool. The note tells the agent to create and remove worktrees with the commands, which covers `git worktree add` and the Bash tool, where no hook reaches. Its `WorktreeCreate` and `WorktreeRemove` hooks run `agent-worktrees hook` for EnterWorktree and a subagent's `isolation: "worktree"`, which Claude Code would otherwise handle itself. The plugin requires the CLI on `PATH`: a configured `WorktreeCreate` hook replaces Claude Code's own creation, so without the CLI every worktree fails, and the plugin does not stand in for the tool. A setup that outruns the Bash tool's timeout leaves the worktree pending, and a rerun of `create` resumes it.

## Claude Code's hook contract

Both hooks receive one JSON object on stdin with `session_id`, `transcript_path`, `cwd`, `hook_event_name` and the event's field: `name` for `WorktreeCreate`, `worktree_path` for `WorktreeRemove`. `WorktreeCreate` takes the first hook that exits 0 with non-empty stdout and uses that stdout, trimmed, as the worktree path; a non-zero exit fails the tool call with the hook's stderr in the message. `WorktreeRemove` runs when the session leaves the worktree; its failures are written to Claude Code's debug log only, so a refusal on removal is seen in `ls` and `prune`, not by the session. A hook's `timeout` is in seconds and defaults to ten minutes; the plugin sets thirty, since a setup that installs a monorepo's packages and a Flutter toolchain on a cold cache runs past ten. Hooks are read once per session, so an installed or updated plugin takes effect in the next session. The hook runs in Claude Code's current directory, which on removal is still the worktree being removed; the tool resolves the primary through `git rev-parse --git-common-dir`, so that is fine. Claude Code caps a name at 64 characters and allows `/` between segments; a name with a `/` is not a worktree name here, since one path segment per worktree is the convention. Subagents with worktree isolation take the same hook with names like `agent-a1b2c3d`, and Claude Code's monthly sweep removes those with `git worktree remove --force` and no hook, which leaves an orphaned ledger entry for `prune`.

## State

The ledger is a directory per worktree at `<git-common-dir>/agent-worktrees/<name>/`, a sibling of git's own `worktrees/` that `git worktree prune` never touches. The entry is created right after `git worktree add` and before setup runs. An empty `ready` file is written when setup exits 0. The primary gets no entry. The entry stays until both teardown and `git worktree remove` have succeeded, so a worktree that is gone while its entry remains is orphaned, and `prune` is the one place that resolves it.

## Names and paths

A name is one path segment, `[A-Za-z0-9._-]+`, accepted by `git check-ref-format --branch`, which also refuses a leading `-`. It is parsed once into its own type at every edge (an argument, a hook's `name`, a hook path's last segment, a ledger directory), and everything below takes that type. The worktree lives at `<primary>/.claude/worktrees/<name>` on the branch `<name>`. That is the path Claude Code uses for its own worktrees, so one directory holds every task checkout and `ls` shows one the tool did not create as unmanaged. `path <name>` prints that path without touching anything.

## Project contract

Any git repository works as it is; a project whose worktrees need more than a checkout adds one or both of two scripts, run with `WORKTREE_PATH` and `WORKTREE_PRIMARY` set and `WORKTREE_NAME` set for a task worktree and unset for the primary. The tool never parses their output; their stdout and stderr both go to the tool's stderr, so stdout carries only the tool's result. `scripts/worktree-setup.sh` runs in the checkout being set up and is read from that checkout. `scripts/worktree-teardown.sh` runs in the primary, is read from the primary, and works from the name alone, since the worktree may already be gone when it runs. Both are rerun on every resume and retry, so each has to be idempotent. A script that exists but is not executable is a refusal, never a silent skip: a skipped setup leaves a checkout that is not ready, and a skipped teardown leaks what the worktree owns.

## Commands

A name's state is read in one place from the ledger, the directory and git's worktree list, and is one of: absent, unmanaged (a directory with no entry), orphaned (an entry with no directory), unlisted (an entry and a directory git does not list as a worktree), pending (an entry without `ready`) or ready. Pending and ready carry what git lists for the path; unmanaged and orphaned carry it when git has it. Every command switches over that state, and the text a person reads for it is rendered by the command line layer alone.

`create <name>` parses the name and then reads the state. Ready: print the path. Unmanaged: refuse, since a directory the tool did not create may hold anything. Orphaned: refuse and point at `prune`, since the teardown of the previous life never ran. Unlisted: refuse, since setup must not run in a directory git does not own; the act is to remove the directory and `prune`. Absent: `git worktree add` on the existing branch, or `-b` for a new one, with git's refusal passed through when it has one, then the ledger entry is created. Absent or pending then runs setup when the project has one, and exit 0, or no setup, writes `ready` and prints the path. A non-zero exit keeps the worktree, the branch and the entry, and refuses with the exit status and the act that resolves it: fix what the script reported and run the same command again. Two concurrent creates of one name are serialized by `git worktree add`, which refuses the second. A word that is not a command is refused rather than taken as a name, so a mistyped command creates nothing.

`init` runs setup, when the project has one, in the current checkout: the primary, with `WORKTREE_NAME` unset, or a task worktree at its conventional path whose state is pending or ready, where a clean exit writes `ready`. Anywhere else it refuses.

`remove [--force] <name>` refuses an absent or unmanaged name, an orphaned one, and a registered directory git does not list as a worktree, whose act is to remove the directory and `prune`. Before anything runs it refuses what `git worktree remove` would refuse after teardown, so teardown cannot release resources for a worktree git then keeps: a locked worktree, always, since the lock is someone's deliberate hold; a worktree containing submodules, and a dirty one by git's own test (a modified tracked file or an untracked file, `--ignore-submodules=none`), both unless `--force`. Teardown runs next when the project has one; a non-zero exit refuses without `--force` and keeps everything. Then `git worktree remove`, with `--force` when asked. The entry is deleted only when both teardown and removal succeeded; with `--force` past a failed teardown the entry stays, `ls` shows it orphaned, and `prune` retries the teardown. The branch is kept, and the command returns the worktree git listed, which the command line prints as the branch kept, or `detached`.

`prune` runs `git worktree prune`, then tears down every entry whose worktree is gone and deletes the entry on exit 0. It tries every entry before refusing with the names whose teardown failed, which stay registered for the next run.

`hook` reads Claude Code's JSON from stdin. `WorktreeCreate` parses `name` as a worktree name, so a nested name is refused as one, runs `create` and prints only the path. `WorktreeRemove` parses the last segment of `worktree_path` the same way, refuses when that path is not the conventional one for the name, and runs `remove --force`, since Claude Code's own removal is forced too and the session that leaves is done with the work. Any other event refuses.

`ls` prints one line per name, tab separated: name, state, branch, path; with none it prints nothing on stdout and notes `no task worktrees` on stderr, so stdout carries results only. The states read `ready`, `setup pending`, `unmanaged`, `orphaned (prune)` and `unlisted`; the branch column reads `detached` for a listed worktree with no branch and `unlisted` when git does not list the path. Names are compared exactly. Only creating a name can alias another, so `create` alone refuses a name that differs only in case from an existing directory or entry, before `git worktree add`, with the act of using the existing spelling; every other command reads the exact name, so a stray `Task-A` beside `task-a` on a case-sensitive filesystem never blocks `remove task-a`, and on a case-insensitive one `Task-A` can neither alias nor damage `task-a`. Every directory under the conventional path is listed, as unmanaged when it has no entry or its name is not a worktree name. Presence is one rule for every command: any entry at the name's path counts, so a file at a worktree name's path is unmanaged, or unlisted when registered, and `ls` shows it; a file whose name is not a worktree name, such as `.DS_Store`, is hidden.

## Output and refusals

Results go to stdout as plain lines. A refusal goes to stderr as `agent-worktrees <command>: <message>` followed by the act that resolves it, and exits 1, or 2 for a usage error: the two statuses the entry point knows. The tool runs only in a plain clone, where the common git directory is the primary checkout's `.git`; a submodule, a bare repository or a separate git dir is refused, since the primary cannot be derived from them. From the primary checkout the derivation is proven, in the one `rev-parse` every command already runs: the git dir is the common dir, so its parent must be the toplevel. From a linked worktree only the common dir's name is checked, since git itself derives the main worktree the same way and reports the wrong one for a separate git dir. A rerun of any command after the act converges: the states are read from the ledger and the filesystem, never remembered.

## Later

`land` fits as one more command on the same ledger: a registered name gives the branch, the primary and the worktree, which is all it needs.
